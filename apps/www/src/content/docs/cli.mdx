The `nimbus-docs` CLI lists what's in the registry, installs it, records what you own in [`nimbus.json`](/project-structure), shows what's fallen behind upstream, and lints your MDX content.

## `nimbus-docs list`

Lists every installable component, utility, and feature.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="list" />

Filter by type:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="list --type ui" />
<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="list --type lib" />
<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="list --type feature" />

Running `nimbus-docs add` with no slug shows the same list.

## `nimbus-docs add <slug>`

Registry entries use two install modes based on their type. Special `adapter-<id>` slugs use a third flow that rewrites project configuration.

### Components and utilities

For `registry:ui` and `registry:lib` slugs, the CLI resolves dependencies, copies files into your repo, and installs any npm packages they need.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add badge" />

<Steps>
  <Step title="Resolve dependencies">
    Walks the slug's `registryDependencies` and any npm `dependencies` it needs.
  </Step>
  <Step title="Copy files">
    Drops each file into the right path under `src/components/ui/`, `src/lib/`, or wherever the entry declares.
  </Step>
  <Step title="Update package.json">
    Adds npm dependencies if they're not already present.
  </Step>
</Steps>

If a component is already installed, `add` keeps your copy — it never clobbers files you own. A component whose files already match the registry is reported as up to date and left alone. Missing files are always added, and `add` lists every file it adds and every differing file it keeps. Pass `--overwrite` to replace files that differ with the registry version (the upgrade path). It lists every file it replaces, and in a terminal it asks first when you've edited the component. Edits are detected from its install record in `nimbus.json` or, for a component that came with the starter, from the starter release your site came from (`--template-dir <path>` compares against a local checkout offline). When neither is available, it asks anyway. Review the change with `git diff`:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add badge --overwrite" />

For `add`, `--yes` assents to prompts such as dependency installs but still keeps existing files. Use `--overwrite` when you actually mean "replace my files."

Once installed, the component lives in your repo. Edit freely — there's no upstream API to break. Each `add` also appends an entry to your [`nimbus.json`](/project-structure) — slug, source registry, the registry release it came from, and a content hash — so later upgrades can track what you own.

### Features

For `registry:feature` slugs, there's nothing to copy. The recipe is a markdown prompt the agent reads, adapts to your project, and applies.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add 404-page" />

If the CLI detects a coding agent in the environment, it prints the recipe to stdout for the agent to consume. Otherwise it prints pipe instructions you can run yourself:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add 404-page --print | claude" />
<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add 404-page --print | codex" />

Use `--print` to force the markdown output, skipping detection.

### Server adapters

For `adapter-cloudflare`, `adapter-vercel`, `adapter-netlify`, and `adapter-node`, the CLI installs the Astro adapter and rewrites the marked `output` block in `astro.config`. It refuses to replace a different adapter or a non-literal `output` value.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add adapter-cloudflare" />

`adapter-cloudflare` adds request rendering when the Nimbus config has no explicit rendering policy. Existing policies are preserved; imported or ambiguous configurations receive a coding-agent handoff instead of a speculative rewrite. The command creates a server-compatible `wrangler.jsonc` when none exists or replaces an unchanged Nimbus static config; custom JSONC and alternate JSON/TOML configs stay untouched.

After completing the adapter install, expect:

```ts
const nimbusConfig = defineNimbusConfig({
  rendering: { default: "request" },
  // ...
});

export default defineConfig({
  output: "server",
  adapter: cloudflare({ prerenderEnvironment: "node" }),
  integrations: [nimbus(nimbusConfig)],
});
```

When the command runs inside a detected coding agent, it emits a versioned recipe so the agent can safely adapt project-owned or split configuration. From a regular shell, use `--print` to request that recipe explicitly:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add adapter-cloudflare --print | claude" />

Always run the project’s production build afterward. See [Rendering policy](/configuration#rendering-policy) for per-collection build/request overrides.

The equivalent long form is `nimbus-docs add server-output --adapter <cloudflare|vercel|netlify|node>`.

## `nimbus-docs init`

Writes a [`nimbus.json`](/project-structure) for a project that lacks one — a repo scaffolded before the record existed, an existing Astro site adopting Nimbus, or a deleted record. Fresh scaffolds already have one, so `init` is the on-ramp for everything else.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="init" />

It scans your installed components, matches each against the registry, and writes what it can recover — marking, never guessing:

- **matched** — byte-identical to the registry copy.
- **modified** — you've edited it; the record keeps the source identity so upgrades can still compare.
- **hand-authored** — yours, from no registry.

The starter version, `templates-v*` tag, and previously reviewed Nimbus version can't be recovered from the repo alone, so they're left blank (and flagged `reconstructed`). Use `migrate --from <version>` to establish the upgrade range.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="init --root packages/docs" comment="scan a nested package (monorepo)" />
<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="init --force" comment="rebuild an existing record" />

## Keeping up to date

Package managers update Nimbus itself; Nimbus updates known API usage and reviews copied code:

```sh
pnpm up @cloudflare/nimbus-docs --latest
pnpm nimbus-docs migrate
pnpm nimbus-docs outdated
```

### `nimbus-docs migrate`

Composes every declared breaking change between the project's `lastReviewedNimbusVersion` and the installed Nimbus version. It shows complete diffs for statically proven edits and bounded review tasks for everything else. Customized or ambiguous code is never forced.

Existing projects without a reviewed baseline must provide the exact Nimbus version whose migrations they last completed:

```sh
pnpm nimbus-docs migrate --from PREVIOUS_VERSION
```

Use `--dry-run` or `--diff` for a read-only plan, `--yes --json` for an agent-safe apply loop, and `--print` for a self-contained Markdown handoff. A computed Astro `srcDir` can be supplied explicitly with `--src-dir <relative-dir>`.

Nimbus applies an edit only when it recognizes the source and can prove the change is safe. Customized or ambiguous code remains unchanged and is returned as a review task. `migrate --print` emits that task for any agent or workflow; Nimbus does not launch one itself.

Migration output includes the selected version range, required reviews, planned diffs, blockers, and errors. Files outside the reported scan boundary are not claimed as checked.

Upgrade entries marked optional appear after required work in `migrate` and as informational Package API notes in `outdated`. They never stop a build. Some only describe an adoption step; others note a change the release makes on its own, such as newly published files, so read each one. Run `migrate --yes` to record them as reviewed when you are ready.

After completing all reported work, explicitly confirm it and advance the committed reviewed baseline:

```sh
pnpm nimbus-docs migrate --from PREVIOUS_VERSION --yes
```

Repeat `--from` only when the project has no recorded baseline. A clean rerun in a terminal asks before recording the reviewed version in `nimbus.json`. Without a terminal, such as in CI or an agent, `migrate` records it only with `--yes`. Nimbus never records completion while a detectable migration remains. Then run `outdated` to review user-owned starter and registry code, followed by `nimbus-docs check`, `astro check`, and the production build. The `migrate` output is the version-selected upgrade guide.

### `nimbus-docs outdated`

The read-only "am I behind?" overview across package APIs, starter files, and registry components:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="outdated" />

- **Package APIs** — points pending source migrations and version-selected reviews to `migrate`. Reviews that only concern API reference pages are skipped when `src/content.config.*` doesn't use `apiCollection` and imports only from Astro, Zod and Nimbus; if it imports anything else (your own files included) or can't be read, every review shows. It also says when a newer Nimbus release is out (looked up on npm; skipped when the lookup fails), and when nothing needs changing but the review isn't recorded yet.
- **Registry components** — compares each recorded content hash against the current registry and classifies the recorded local footprint, and lists npm dependencies installed below the version a component needs, with the command to update them. Registry updates remain review-only because overwrite can also affect dependencies.
- **Starter files** — compares your scaffolded `src/` files, plus `AGENT.md`, `CLAUDE.md`, and `tsconfig.json`, against the upstream `templates-v*` tag, including additions and removals. Because those files came from a tag that was never in your git history, plain `git diff` can't show this. Content files are hidden by default (`--all` to include them). Files every site rewrites, such as `package.json`, `wrangler.jsonc`, and `nimbus.json`, aren't compared; changes to them come through `migrate`.

Pass `--json` for agent-readable findings; apart from the `newer-release` warning, they depend only on the project. `summary.packageApis` counts every migration and upgrade review, and `summary.requiredPackageApis` counts the required ones. `warnings` flags a compared starter that needs a newer package than the project has (`starter-needs-newer-package`), which also blocks `diff --apply`. Projects without complete `nimbus.json` provenance still receive Package API results and an explicit partial-coverage result.

### `nimbus-docs diff [file]`

Read-only detail for starter files — what you changed, and what changed upstream:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="diff" comment="every changed starter file" />
<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="diff src/components/ui/aside/Aside.astro" comment="one file" />

Each file is one of: **clean to pull** (upstream changed, you didn't), **added/removed upstream**, **hand-merge** (you both changed it), or **your changes** (you edited it, upstream didn't; `--apply` reports that there's nothing to pull and keeps your edits). For clean updates, additions, and removals, you can let the CLI apply one reviewed change:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="diff src/components/ui/aside/Aside.astro --apply" />

`--apply` is explicit and per-file, rejects symlink/path escapes, and rechecks the clean preimage or absence before writing — it never merges. It records the tag it took the file from in `nimbus.json` (`templatesTagByFile`), so later diffs compare that file from there. Review with `git diff` afterward. Pass `--to <templates-vX.Y.Z>` to target a specific tag, or `--template-dir <path>` to compare offline against a local checkout.

## `nimbus-docs check`

A build-free preflight. It checks the environment, project structure, pending migrations, authoring rules, and types, then reports whether the site can build:

```sh
pnpm nimbus-docs check
```

Pass `--env`, `--structure`, `--migrations`, `--lint`, or `--types` to run only those categories. `--fix` applies the fixes it can make safely and asks before any fix that needs a value or installs a dependency. Without a terminal it skips the questions and installs only with `--yes`. `--quiet` shows errors only.

`--types` type-checks your `.ts` and `.tsx` files with your own TypeScript. It doesn't read `.astro` files; run `astro check` for those.

`check` exits `1` when an error-severity finding remains, and `0` otherwise. Warnings, informational findings, and checks that couldn't run never change the exit code.

Pass `--json` for agent-readable output. `status` is `passed`, `failed`, or `partial` (some checks couldn't run), and `readiness` is `buildable`, `blocked`, or `unknown`. Each finding has one of three severities:

| Severity | Meaning |
|---|---|
| `error` | Must be fixed. Counted in `summary.errors` and sets the exit code to `1`. |
| `warn` | Advisory, such as the placeholder `site` URL. Counted in `summary.warnings`. |
| `info` | Informational only, such as an optional upgrade entry from `migrate`. Not counted in the summary. |

Checks that couldn't run are listed as `notes` on their scope rather than as findings, each with the reason it was skipped. In the terminal, a scope with notes shows `◐ ok, partly checked`.

`check` checks links only when an earlier `astro build` left `.nimbus/routes.json`; without it, link checking is a note, not an error. To gate CI on links, run `astro build` and then `nimbus-docs lint`; see [Check links](/writing/linting#check-links).

## `nimbus-docs lint`

Walks `src/content/` and the checkout of each [content source](/writing/content-sources), runs each authoring rule you've enabled, prints diagnostics, and exits non-zero when any `error`-severity finding survives. The build is never gated by lint — drafts that fail lint still render under `astro dev`.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="lint" />

Flags — combine with `lint`:

| Flag | Effect |
|---|---|
| `--format=json` | agent-readable diagnostics |
| `--rule=nimbus/single-h1` | run one rule only |
| `--fix` | apply auto-fixes in place |
| `--quiet` | errors only, suppress warnings |

Severity overrides live with the integration (`nimbus(config, { rules })`), and `astro build`, `astro dev` or `astro sync` writes them to `.nimbus/lint.json`. If you've changed the rules since, `lint` says so and asks you to run `astro sync`. Without that file, `lint` exits `1` and asks you to build first, unless `--rule` names a rule to run. In-file disables (`nimbusDisableRules` frontmatter, inline comments) work with no config.

`nimbus/internal-link` and `nimbus/redirected-link` need `astro build` to run first. Without the route list the build writes, lint exits `1` with an error on `.nimbus/routes.json`.
