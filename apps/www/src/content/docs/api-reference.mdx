Nimbus generates API references from machine-readable specifications. Each supported format has its own source, configuration, and content loader.

## OpenAPI

Nimbus currently supports OpenAPI 3.x. Nimbus turns a local OpenAPI document into a content collection that powers reference pages, navigation, alternate Markdown versions, search entries, `llms.txt` indexes, and stable links from prose documentation.

The OpenAPI document remains the source of truth. You do not create one MDX file per operation or schema.

### Install with the recipe

Start with an OpenAPI 3.x document stored in your repository. If you have a Swagger 2.0 document, [convert it first](#convert-a-swagger-20-document). `src/api/openapi.yaml` is the usual location, but Nimbus accepts any project-relative local path or an inline document object. Remote specification URLs are not supported.

Run the API reference recipe from the project root inside your coding agent:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add api-reference" />

Nimbus passes the recipe directly to detected coding agents. From a regular shell, add `--print` and pass the output to your coding agent. Without `--print` and outside a detected agent, the command changes no files and prints nothing on standard output, with or without a terminal: it writes instructions for piping the recipe to an agent to standard error. Scripts should pass `--print`. The recipe reviews its plan before changing files.

The recipe tells the agent to inspect your project, ask for the specification path and collection name, and then:

1. Installs the editable API layout and its parser dependencies.
2. Declares the specification in the Nimbus config in `astro.config.ts`.
3. Registers a loader-backed Astro content collection with one line.
4. Adds the HTML catch-all route. The starter's shared Markdown route serves each page's Markdown version.
5. Connects the collection to search, alternate Markdown versions, and `llms.txt` indexes.

### Convert a Swagger 2.0 document

Nimbus reads OpenAPI 3.x only. A Swagger 2.0 document fails the build with `Swagger 2.0 isn't supported. Convert it to OpenAPI 3.x first.`, followed by the document's path.

Keep the Swagger document as your source, and generate a separate OpenAPI 3.x document from it with [swagger2openapi](https://github.com/Mermade/oas-kit/tree/main/packages/swagger2openapi):

<PackageManagers pkg="swagger2openapi@7.0.8" dev />

Run the conversion before Astro in your `dev` and `build` scripts, so the generated document always matches its source:

```json title="package.json"
{
  "scripts": {
    "dev": "swagger2openapi src/api/swagger.yaml --yaml --outfile src/api/openapi.yaml && astro dev",
    "build": "swagger2openapi src/api/swagger.yaml --yaml --outfile src/api/openapi.yaml && astro build"
  }
}
```

Point the `api` entry's `spec` at the generated document, `./src/api/openapi.yaml`. The converter turns `host`, `basePath`, and `schemes` into `servers`, moves body and form parameters into request bodies, and converts security definitions. The development server watches the generated document, not the Swagger source, so restart `dev` after editing the source.

### How the pieces fit


| File | Responsibility |
| --- | --- |
| `src/api/openapi.yaml` | The API contract and documentation source. |
| `astro.config.ts` | Declares the specification, versions, routes, and rendering policy in the Nimbus config. |
| `src/content.config.ts` | Registers the generated entries as an Astro content collection. |
| `src/pages/api/[...slug].astro` | Renders API HTML through the user-owned API layout. |
| `src/pages/[...slug]/index.md.ts` | The starter's shared Markdown route. Serves an alternate Markdown version of every API page. |
| `src/components/ui/api-*/` | Owns the reference's appearance and interaction design. |

#### Why the specification is not in `src/content`

`src/content/docs/` contains authored MDX entries. An OpenAPI document is an input to a loader: Nimbus projects it into many operation, tag, and webhook entries in the registered `api` collection, plus schema entries when [schema pages](#schema-pages) are on.

Keeping the source under `src/api/` makes that distinction visible. The path is only a convention; `src/content/api/openapi.yaml` also works if the configured `spec` points there.

### Configuration generated by the recipe

The recipe declares the specification once, as an `api` entry in the Nimbus config:

```ts title="astro.config.ts"
import { defineConfig } from "astro/config";
import nimbus, {
  defineConfig as defineNimbusConfig,
} from "@cloudflare/nimbus-docs";

const nimbusConfig = defineNimbusConfig({
  site: "https://docs.example.com",
  title: "Acme Docs",
  api: [
    {
      collection: "api",
      spec: "./src/api/openapi.yaml",
    },
  ],
});

export default defineConfig({
  integrations: [nimbus(nimbusConfig)],
});
```

The collection name is also its URL prefix: `api` mounts the reference at `/api`.

The recipe then registers a loader-backed collection under the same key, preserving existing collections and custom schema fields:

```ts title="src/content.config.ts"
import { defineCollection } from "astro:content";
import {
  apiCollection,
  docsCollection,
  partialsCollection,
} from "@cloudflare/nimbus-docs/content";

export const collections = {
  docs: defineCollection(docsCollection()),
  partials: defineCollection(partialsCollection()),
  api: defineCollection(apiCollection()),
};
```

`apiCollection()` reads the `api` entry whose `collection` matches its key, so the specification is declared only once. The key tells Astro which loader turns that entry into content entries, and lets Nimbus find the collection during configuration and build validation.

To mount several specifications, add one `api` entry and one `apiCollection()` line for each. The build fails if a collection key has no `api` entry, or an `api` entry has no matching `apiCollection()` under its key. The error names both files. `nimbus-docs check` reports the same mismatches without a build.

In `astro dev`, editing a spec file re-indexes its pages. Editing the `api` entries restarts the dev server and re-indexes the reference, without a manual restart.

#### Passing the entry explicitly

`apiCollection()` also accepts the entry directly: `apiCollection({ collection: "api", spec: "./src/api/openapi.yaml" })`. Sites created by earlier versions of the recipe use this form, with the Nimbus config in a separate `nimbus.config.ts` built with `defineConfig` from `@cloudflare/nimbus-docs/config`. They keep building unchanged. Moving the config back into `astro.config.ts` and switching to `apiCollection()` lets `nimbus-docs check` validate the config statically, lets `add adapter-cloudflare` edit it in place, and re-indexes edits to the `api` entries in `astro dev`.

### Coordinates and routes

Nimbus treats identity and routing separately. A **coordinate** identifies an API item in citations, cross-version matching, anchors, and the coordinate manifest. A **route** is the URL of its generated page.

Operations use their OpenAPI `operationId` as the coordinate:

```yaml
paths:
  /v1/events/{event_id}:
    get:
      operationId: retrieveEvent
      summary: Retrieve an event
      tags: [Events]
```

This operation's coordinate is `retrieveEvent`. Without a route policy, its first tag and operation ID produce `/api/Events/retrieveEvent`.

The optional `resource-action-v1` policy instead derives routes from HTTP methods and paths:

```ts
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    requireOperationId: true,
    routes: {
      convention: "resource-action-v1",
      stripPathPrefixes: ["/v1"],
    },
  },
],
```

Here, Nimbus removes `/v1` and publishes the operation at `/api/events/retrieve`; its coordinate remains `retrieveEvent`.

Derivation recognizes `/<resource>` and `/<resource>/{parameter}` after prefix removal. It maps collection `GET`/`POST` to `list`/`create`, and member `GET`/`PUT`/`PATCH`/`DELETE` to `retrieve`/`update`/`update`/`delete`. Tags do not affect policy routes. Other shapes or unsupported method/shape combinations normally fall back to a normalized coordinate with a build warning; the build fails if that coordinate cannot produce a non-empty route.

An explicit operation override, keyed by the exact usable `operationId`, takes precedence and can preserve an existing URL or handle a path that cannot be derived:

```ts
routes: {
  convention: "resource-action-v1",
  operations: {
    retrieveEvent: "events/get",
  },
},
```

Without a usable `operationId`, Nimbus derives a fallback coordinate from the method and path. `requireOperationId: true` rejects that fallback, but changing an existing operation ID still changes the coordinate. Webhooks always use their map keys as coordinates and publish below `webhooks/<key>`; configuring an operation override for a webhook fails the build.

Renaming a coordinate requires updating citations and affects cross-version matching. Changing only a route leaves coordinate-based citations intact, but breaks direct links to the previous URL. Nimbus does not create that redirect automatically; add it in Astro or on the deployment platform.

#### Link from prose by coordinate

Use an `api.ref:` destination in Markdown or MDX under `src/content`:

```md
See how to [retrieve an event](api.ref:api:retrieveEvent).
```

Nimbus resolves the citation during the build:

- `api` identifies the API collection.
- `retrieveEvent` identifies the operation independently of its route.
- A citation without a version targets the API family's default version.
- An unknown coordinate in a known collection fails the authored-content build and may suggest a close match.
- An unknown collection is warned and rewritten to `#`; verify collection names against `/nimbus-api/coordinates.json` so dead citations do not ship.

Pin a historical version only when the prose specifically discusses it:

```md
Review the [v1 operation](api.ref:api@v1:retrieveEvent).
```

#### Coordinate shapes

Operations are not the only addressable items. Nimbus assigns coordinates to pages and to details within them:

| API item | Coordinate example |
| --- | --- |
| API root | `api` |
| Tag | `tags.Events` |
| Operation | `retrieveEvent` |
| Request body field | `retrieveEvent.name` |
| Parameter | `retrieveEvent.path.event_id` |
| Response | `retrieveEvent.response.200` |
| Response field in an additional media type | `retrieveEvent.response.200.text-csv.id` |
| Schema (with [schema pages](#schema-pages) on) | `Event` |
| Schema field (with schema pages on) | `Event.created_at` |
| Webhook | `delivery.succeeded` |

Use `/nimbus-api/coordinates.json` to inspect the exact coordinates and resolved URLs published by a built site.

### Versioned API references

API versions live inside the `api` entry. This is separate from the top-level `versions` option used for authored prose documentation. An entry accepts either `spec` for one version or `versions` for a family, not both. This example uses the default operation-ID routes; route policies are set independently on each version:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    label: "Acme API",
    requireOperationId: true,
    versions: [
      {
        version: "v2",
        spec: "./src/api/openapi-v2.yaml",
        default: true,
        status: "ga",
      },
      {
        version: "v1",
        spec: "./src/api/openapi-v1.yaml",
        status: "deprecated",
      },
    ],
  },
],
```

The version marked `default: true` owns `/api`; other versions mount below their version, such as `/api/v1`. If none is marked, the first version is the default. A deprecated version renders its status in the reference UI.

The version picker keeps readers on the same page when they switch versions. Nimbus links pages across versions in this order:

1. **Same coordinate.** Pages that share a coordinate, such as the same `operationId`, are the same page. This link always wins.
2. **Same method and path.** When an `operationId` changed between versions, an operation links to the one with the same HTTP method and path. A path segment that is a single parameter may be renamed, so `/zones/{zone_id}` matches `/zones/{id}`, but `{name}.{format}` must stay the same. Among operations not already linked between the two versions, the match must be the only one on each side. Links chain across versions, so a v1 page can link to a v3 page through v2.
3. **No match.** An ambiguous or conflicting match links nothing, and the picker opens the other version's landing page.

Route policies belong to each version in a version family. This makes URL decisions explicit when two specifications use different base paths or need different overrides.

#### Versions in the query

A request-rendered family can keep one path per operation and select the version with a query parameter instead of a path prefix. Query mode needs `versions` and request rendering for the family, since a static file is the same whatever the query says:

```ts title="astro.config.ts"
rendering: { default: "request" },
api: [
  {
    collection: "api",
    label: "Acme API",
    versionMode: "query",
    versions: [
      { version: "v2", spec: "./src/api/openapi-v2.yaml", default: true },
      { version: "v1", spec: "./src/api/openapi-v1.yaml" },
      { version: "2026-11-30.preview", spec: "./src/api/openapi-preview.yaml", hidden: true },
    ],
  },
],
```

Every version serves from the family's own path: `/api/pets/` renders the default version, `/api/pets/?api-version=v1` renders `v1`, and an unknown id, or `api-version` given more than once, returns the 404 page. An empty `api-version` selects the default. An operation keeps its path across versions only while its slug does: with the default operation ID routes, an operation renamed between versions has a different path in each, and the version picker links them. Version-prefixed paths such as `/api/v1/pets/` do not exist in this mode. Inside a non-default version, every generated same-version link — page body, navigation, breadcrumbs, citations, the picker's active item — carries that version's `api-version` query, so readers stay in the version they chose.

Discovery stays version-free: the sitemap, alternate Markdown, and `llms.txt` describe the default version at the plain URLs. Non-default pages are `noindex`, with their default counterpart as canonical; a page with no default counterpart has no canonical. Per-page Markdown exists for the default version only: a `.md` URL serves the default version whatever its `api-version` says, and a non-default page requested with `Accept: text/markdown` answers with its HTML. A hidden version's pages are reached only by its query, but `hidden` is not access control: `/nimbus-api/coordinates.json` lists them, and its spec is published at `/api/<version>/openapi.json` unless the version sets `publishSpec: false`.

If a cache sits in front of the site, its cache key must keep the `api-version` parameter and vary on `Accept`, or readers get another version's page or the wrong format.

Sites that don't set `versionMode` keep path versions unchanged, with one exception that applies in both modes: a version id uses lowercase letters, digits, dots, and dashes, and starts and ends with a letter or digit (`2026-11-30.air`). An existing id such as `-v1` or `v1-` must be renamed.

### Sidebar for large APIs

By default, every API page includes the whole navigation tree. For a large API, that tree can be most of each page's size. Set `sidebar` on the `api` entry to include less:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    sidebar: "on-demand",
  },
],
```

| Value | What each page includes | A collapsed group |
| --- | --- | --- |
| `"full"` (default) | The whole tree. | Opens in place. |
| `"on-demand"` | Top-level items, plus the current page's branch. | Opens in place, loading its rows the first time. |

With `"on-demand"`, the current page's ancestors are open and show all their children, so its neighbors are one click away. Schema and webhook pages show top-level items only. The setting applies to every version of a family.

When a reader opens a collapsed group, the sidebar fetches the page its label links to and copies the group's rows from that page's sidebar. A group without a page, such as an `x-tagGroups` category, takes its rows from the API overview instead. Fetching starts when the pointer moves over a group or it receives focus, so rows usually appear as soon as it opens. If they cannot load, opening the group goes to its page instead.

Without JavaScript, a collapsed group's label still links to its page. Categories from `x-tagGroups` have no page to link to, so they open only on pages inside them; the API overview's body links every section.

Every page still carries every top-level item, so an API with hundreds of flat tags stays heavy. Group its tags under a tag's `parent` or with `x-tagGroups`, which Nimbus reads in any OpenAPI version. A tag's `x-displayName` sets the label readers see, while its `name` keeps deciding its coordinate and route:

```yaml title="openapi.yaml"
tags:
  - name: workers
    x-displayName: Workers
  - name: workers.scripts
    x-displayName: Scripts
    parent: workers
```

In every mode, the sidebar keeps the groups a reader opened and its scroll position from page to page for the rest of the session, in the desktop rail and the mobile drawer. Restored groups appear already open. Rows loaded on one page show on the next before it paints; a new deployment starts over, so rows saved before it are never shown after it.

The API rail renders the same markup as the docs sidebar: groups are native `<details>`/`<summary>` rows styled by the `nb-sidebar-row`, `nb-sidebar-link`, and `nb-sidebar-list` classes in `src/styles/globals.css`, a group's page lists as its first "Overview" child, and each page renders one tree that the mobile drawer borrows while open. See [Sidebar — markup and styling hooks](/navigation/sidebar#markup-and-styling-hooks).

Set `sidebar` on the `api` entry in the Nimbus config. A site that passes its entry to `apiCollection({ … })` still takes the mode from the config, and the build warns if the two disagree.

Every group page lists its operations and its subsections, and the API overview lists every top-level section, so all pages stay reachable in every mode.

#### Upgrading an existing site

`"on-demand"` needs API sidebar and layout components from the same release as your `@cloudflare/nimbus-docs`. With older copies, the build fails and names the outdated files. To update them, run:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add api-layout" />

For each component already in your project, it asks whether to overwrite it, even if your copy is unchanged. Choose **Overwrite** for `api-layout` and `api-sidebar`, which replaces your edits to those two, and **Skip** for the rest to keep yours. `--overwrite` skips the questions and replaces every component `api-layout` uses, including the docs sidebar.

Components come from the registry on nimbus-docs.com, which is updated shortly after each release. If `add` warns that the registry is older than your project, the new components aren't published yet: keep `sidebar: "full"` and try again later.

### Published spec

Each collection publishes its spec as one self-contained JSON file at `/api/openapi.json`, with versions at their own mount path, and lists it in the site's API catalog. Set `publishSpec: false` on a collection, or on a single version, to keep that spec unpublished:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    publishSpec: false,
  },
],
```

### Schema pages

By default, types show only inline, on the operations that use them: request and response fields, and the properties previewed under each union variant, come from `components/schemas`, but a schema gets no page of its own. In a large API, schema pages would outnumber operation pages.

To publish a page for every schema at `/api/schemas/<Name>`, set `schemaPages: true`:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    schemaPages: true,
  },
],
```

Each schema then also gets:

- a Markdown version and an OG image;
- sitemap, search, and `llms.txt` entries;
- coordinates, for the schema and its fields, in citations and `coordinates.json`.

Type names such as union variants, discriminator mappings, and `map<Name>` value types link to their schema pages; without them, they render as text. A union variant previews its properties one level deep, so turn schema pages on if readers need a variant's nested fields.

With schema pages off, an `api.ref:` citation in your content to a schema or a schema field fails the build and names the setting. Cite an operation that uses the type instead. Schema names claim their `schemas/<Name>` routes either way, so turning schema pages on can't collide with an operation. The setting applies to every version of a family.

### Code samples

Each operation page shows the request in cURL, TypeScript, and Python. Parameter values come from the specification:

- A parameter's own `example`, or its first `examples` entry, comes first.
- Otherwise the value is generated from the parameter's schema with [openapi-sampler](https://github.com/Redocly/openapi-sampler), the same way request bodies are. Without a declared value, it's a type guess, such as `string`, `0`, or a format's stock value.
- A path parameter keeps the generated value only when a value declared in its schema produces it: an `example`, `const`, `examples`, `enum`, or `default` in a part of the schema the sampler reads. Those parts are every `allOf` member, the first `oneOf` branch (or the first `anyOf` branch when there's no `oneOf`), and `if` with `then`. Otherwise it shows its name in angle brackets, such as `<account_id>`: a guessed identifier would name no real resource.
- Required query parameters and headers keep the generated value, guesses included. One with no schema, or whose generated value is an array or object, shows `<name>`.

Credentials always render as placeholders: `Bearer <token>`, `Basic <credentials>`, or the API key's name, such as `<X-API-Key>`. Placeholders are never URL-encoded; declared values are, as in a real request. Request bodies use the request example, or a value generated from the schema.

For methods that support a request body, an explicit JSON `null` is sent as the four bytes `null` in every generated language. It is distinct from an absent body. Without an authored example, Nimbus still generates a value from a usable schema.

An `application/x-www-form-urlencoded` body is sent as form fields. A property with an entry in the media type's `encoding` follows it: `style`, `explode`, or `allowReserved` select query-style serialization, and an entry without them sends the value as its `contentType`, so an object is sent as JSON. A `deepObject` property indexes every array (`expand[0]=customer`). A property without an `encoding` entry uses the bracket convention common to form APIs, not OpenAPI's JSON default: nested objects in brackets (`metadata[plan]=pro`), the name repeated for each item of a scalar array (`tags=a&tags=b`), and arrays of objects indexed (`items[0][price]=p_1`). A string example is read as an encoded form. A `null` field is sent as an empty value (`name=`), the same as `""`; a JSON `contentType` sends it as `null`. Empty objects and arrays send no fields, and any other example sends no body.

For example, this media type sends `tags` joined with commas and `metadata` in brackets:

```yaml
application/x-www-form-urlencoded:
  schema:
    type: object
    properties:
      tags: { type: array, items: { type: string } }
      metadata: { type: object, additionalProperties: { type: string } }
  encoding:
    tags: { style: form, explode: false }
  example:
    tags: ["a,b", "c"]
    metadata: { plan: pro }
```

```text
tags=a%2Cb,c&metadata%5Bplan%5D=pro
```

With `explode: false`, items are joined with `,` (`form`), `|` (`pipeDelimited`), or `%20` (`spaceDelimited`), and each item is encoded first, so a separator inside an item stays distinct from the one between items. With `allowReserved: true`, a `,` inside an item is sent unencoded as OpenAPI specifies, so `["a,b", "c"]` and `["a", "b,c"]` send the same bytes; use `allowReserved: false` or a JSON `contentType` when items can contain separators. With `explode: true`, or a JSON `contentType`, an array repeats the field once per item.

An explicit JSON `contentType`, including a `+json` media type, JSON-serializes each field value before form encoding: a string such as `abc` is sent as `%22abc%22`. With `allowReserved: true`, valid percent-encoded triples and safe reserved characters pass through unchanged; form delimiters (`=`, `&`, `+`) and unsafe characters (`[`, `]`, `#`) stay encoded. Forms using reserved expansion are sent as pre-encoded text so the HTTP client does not encode them again.

```sh
curl --request GET \
  --url 'https://api.example.com/accounts/<account_id>' \
  --header 'Authorization: Bearer <token>'
```

An operation's `x-codeSamples` replace the generated samples, and Nimbus never changes their text. Every entry is shown, in order, including several in one language, such as an SDK call and a raw request in Python. Each entry's `label` names it in the code rail's picker and in the page's Markdown version. An entry without a `label` uses its `lang`, and a repeated name is numbered: `Python`, `Python (2)`.

Giving each sample in one language its own picker option needs the `api-code-rail` component from 0.16.0 or later. To update it, run `nimbus-docs add api-code-rail` and choose **Overwrite** for `ApiCodeRail.astro` and `code-rail.client.ts`, and **Skip** for the other components.

If the installed httpsnippet writes a body in a layout Nimbus doesn't recognize, that language's sample is left out rather than shown with a wrong body; the other languages are unaffected. On the page, the request body appears inside the code samples, and the page's Markdown version also lists it as an example request. An operation with no samples at all, such as with `samples.generate: []` and no `x-codeSamples`, shows its request example on the page instead. That needs the `api-layout` component from this release: commit first, then run `nimbus-docs add api-layout --overwrite`. It also replaces the components it depends on, including the sidebar, so review the change with `git diff` and reapply your own edits.

Two settings on the `api` entry control generated samples. `samples.generate` picks the languages Nimbus generates, on every operation; it defaults to all three, and `[]` generates none. `samples.keepGenerated` keeps generated languages next to authored samples. For example, to generate only cURL, and show it next to any authored SDK samples:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    samples: { generate: ["curl"], keepGenerated: ["curl"] },
  },
],
```

Kept samples follow the authored ones. An authored sample in the same language replaces the generated one: `curl`, `python` or `py`, and `typescript` or `ts`, in any case. An authored `shell` or `bash` sample does not replace cURL. Every `keepGenerated` language must also be in `generate`. Valid values for both are `"curl"`, `"typescript"`, and `"python"`. The settings apply to every version of a family.

The code rail remembers the reader's language, not the exact sample: choosing a second Python sample opens the first Python sample on the next operation. A `?lang=` link opens the sample with that id, such as `python-2`, or the first sample in that language, such as `python`.

### Build or request rendering

API HTML is prerendered by default. To render only the API collection on request, add this policy to the Nimbus config:

```ts title="astro.config.ts"
rendering: {
  default: "build",
  collections: {
    api: "request",
  },
},
```

Then run the Cloudflare adapter installer. It keeps an existing rendering policy. Without one, it sets `rendering: { default: "request" }`, which renders every collection on request.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add adapter-cloudflare" />

Astro then logs "getStaticPaths() ignored in dynamic page" for the request-rendered API route. The warning is expected; see [Mix build and request rendering](/configuration#mix-build-and-request-rendering).

The recipe's API catch-all uses Nimbus runtime helpers to resolve either mode. Request rendering changes the canonical HTML pages only. Alternate Markdown versions, coordinate data, search records, sitemaps, and `llms.txt` indexes remain build products, and requests consume prepared content entries rather than parsing the OpenAPI document.

#### Large APIs and many versions

A request-rendered API bundles its page data into the server. That suits most APIs. For a very large spec, or one that keeps many versions, set `bundle: false` on its entry so the server bundle stays small however many versions you add:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    versions: [/* … */],
    bundle: false,
  },
],
rendering: {
  collections: { api: "request" },
},
```

Nimbus then writes each page's data as static assets beside the site, shares unchanged pages between versions, and reads one version's index plus the requested page on each request. Each build also ships the previous successful build's page files, so a server still running that release during a rollout (for example a Node server in a blue-green swap) keeps working; on Cloudflare each Worker version already keeps its own files. The build suggests `bundle: false` when an API's bundled page data passes 16 MiB.

Pages are read through an Astro live collection, which Astro only accepts from your own `src/live.config.ts`. Add it once; the build shows this snippet if it's missing:

```ts title="src/live.config.ts"
import { defineLiveCollection } from "astro:content";
import { apiPagesLoader } from "@cloudflare/nimbus-docs/live";

export const collections = {
  apiPages: defineLiveCollection({ loader: apiPagesLoader() }),
};
```

When Astro's route cache is enabled, each page is cached with the tags `nimbus-api:<collection>` and `nimbus-api:<collection>@<version>`.

`bundle: false` needs the collection rendered on request and the Cloudflare or Node adapter; the build explains what to change otherwise. It also changes discovery for that API: search, `llms.txt`, the sitemap and Markdown versions cover the default version only. Older versions stay readable as HTML, with `noindex`, and their Markdown returns 404.

Version pickers use one runtime helper in every rendering mode:

```ts
const href = await getVersionSwitchUrl({
  collection: "api",
  sourceVersion: "2026-10-09",
  id: coordinate,
  targetVersion: "2026-10-02",
});
```

Import it from `@cloudflare/nimbus-docs/runtime` and apply `withBase` once when rendering the link. Pass the page's exact source version, including on the latest version's pages. The link goes to the same operation in the target version, or to that version's landing page when the operation doesn't exist there.

For custom API heads, use `getApiVersionHead(collection, version, coordinate, request)` for the canonical link and the alternate versions; the starter's `ApiLayout` uses it too. `getApiVersionAlternates` still works, except for an API with `bundle: false`, where it throws `NIMBUS_API_EAGER_ALTERNATES` and the build points at any component that calls it. See upgrade entry `api-request-path`.

With `bundle: false`, Nimbus reuses the versions you didn't change. In CI, restore `.nimbus/cache/page-assets/` before the build and save it after a successful deploy, not after preview builds, so "previous" means the live release; restore the whole directory. Key the cache by project, with a fallback key so adding a version keeps the earlier entries. Nimbus checks the cache's contents itself and rebuilds anything missing or damaged, so keep your specs in the repository, not only in the cache. Upgrading Nimbus can rebuild every version once.

#### Prepared code examples

`apiCollection()` highlights request samples, primary and named request examples, responses, and the examples of additional request body and response media types while it builds the content index. OpenAPI `requestBody.content.*.examples` entries are available as `ApiOperationPage.requestExamples`, preserving each key, summary, description, media type, and inline value. External-only examples are not fetched.

User-owned renderers should render `highlightedHtml` with Astro's `set:html` rather than importing Shiki or Astro's `Code` component into a request-rendered route:

```astro
---
import type { ApiOperationPage } from "@cloudflare/nimbus-docs/api";

interface Props extends Pick<ApiOperationPage, "samples"> {}

const { samples } = Astro.props;

function preparedCode(value: { highlightedHtml?: string }): string {
  if (!value.highlightedHtml) {
    throw new Error("Nimbus API code was not prepared during content sync.");
  }
  return value.highlightedHtml;
}
---

{samples.map((sample) => (
  <Fragment set:html={preparedCode(sample)} />
))}
```

Treat a missing prepared value as a stale or incorrectly built API index. Rebuild after changing the specification or API renderer types.

See [Configuration](/configuration#rendering-policy) for the Cloudflare adapter and Wrangler requirements.

### Published outputs

For a collection named `api`, the reference integrates with these routes when their corresponding starter routes are present:

| Route | Purpose |
| --- | --- |
| `/api` | Default-version API overview. |
| `/api/<page-slug>` | Operation, tag, or webhook page, and schema pages with [`schemaPages: true`](#schema-pages). |
| `/api/<page-slug>/index.md` | Clean Markdown version. |
| `/api/llms.txt` | API-only `llms.txt` index. |
| `/llms.txt` | Site-wide page index. |
| `/nimbus-api/coordinates.json` | Public coordinate-to-URL manifest. |

The API entries also join the existing Pagefind search, sitemap, and OG-image routes when those features are enabled in the project.

### Cite an API hosted elsewhere

A documentation site can cite a reference published by another Nimbus site without mounting or republishing it:

```ts
apiReferences: [
  {
    collection: "api",
    manifest: "https://api.example.com/nimbus-api/coordinates.json",
    origin: "https://api.example.com",
  },
],
```

`collection` must match the collection key published by the remote manifest. `origin` is the absolute prefix prepended to site-relative manifest paths. Include the deployment base when the remote reference is hosted below one, for example `https://api.example.com/docs`.

The remote collection then uses the same prose syntax: `api.ref:api:retrieveEvent`. Remote references provide citation targets only; they do not add the remote pages to local search or agent outputs.

The manifest lists each page's path without a trailing slash, and it doesn't record the remote site's `trailingSlash`. With `origin`, citations use the path as listed, so on a remote site that serves `/api/retrieve-event/`, a citation links to `/api/retrieve-event`, which that site may redirect or answer with 404. Without `origin`, the paths stay site-relative and take this site's trailing-slash shape, which is right only when both sites use the same `trailingSlash` and `build.format`. Check a citation against the remote site before relying on it.

Nimbus fetches HTTPS manifests during the build. An unavailable or malformed remote manifest produces warnings and its citations resolve to `#`; it does not stop the build. You can instead commit a manifest and use a project-relative path when builds must work offline. An unreadable local manifest, invalid JSON, or invalid top-level shape fails the build; malformed entries inside an otherwise valid manifest are warned and ignored.

### Verify the reference

Run a production build after adding or changing a specification:

```sh
pnpm build
```

Confirm that:

1. The build reports the number of indexed API pages.
2. `/api` and one operation page render.
3. The same operation's `/index.md` route returns Markdown.
4. `/api/llms.txt` lists the reference pages.
5. `/nimbus-api/coordinates.json` contains a known operation ID.
6. A prose `api.ref:` link resolves to the expected route.

For request rendering, test the production Worker locally with Wrangler rather than relying only on Astro's development server.
