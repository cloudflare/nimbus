Nimbus builds a typed sidebar tree from your content. Start with the filesystem, take control with configuration, or transform the final tree for navigation that depends on application data or the current route.

## Generate from the filesystem

The sidebar is generated from `src/content/docs/` by default. Set `sidebar.items` in `astro.config.ts` only when you need to override that structure. Use `sidebar.order` in a page's frontmatter, such as `src/content/docs/get-started.mdx`, to control ordering; otherwise entries are alphabetical.

```yaml title="src/content/docs/get-started.mdx"
---
title: Get started
sidebar:
  order: 1
  label: Quickstart
  badge:
    text: New
    variant: tip
---
```

Frontmatter can also hide entries, customize directory groups, redirect links, or collapse a section. See [Per-page controls](#per-page-controls).

## Define the structure

In `astro.config.ts`, use `sidebar.items` when the filesystem should not define the entire rail. Config items can be nested and can mix manual links with generated content:

```ts title="astro.config.ts"
sidebar: {
  items: [
    "introduction",
    { label: "GitHub", link: "https://github.com/you/repo" },
    {
      label: "Guides",
      autogenerate: { directory: "guides" },
      collapsed: false,
      badge: "New",
      icon: "ph:book-open",
    },
    {
      label: "API",
      autogenerate: { collection: "api" },
      icon: "ph:code",
    },
    {
      label: "AI",
      segment: "/ai",
      landing: "/ai/models",
      items: [
        { label: "Models", link: "/ai/models" },
        { autogenerate: { directory: "ai/guides" } },
      ],
    },
  ],
}
```

| Shape | Use |
|---|---|
| `"slug"` | Link one page from the primary collection. |
| `{ label, link }` | Add a labeled internal or external link. |
| `{ autogenerate: { directory } }` | Generate a group from one content directory. |
| `{ autogenerate: { collection, prefix? } }` | Mount another registered collection, linked where it's served ([Collection URLs](/writing/pages-and-routing#collection-urls)). `prefix` sets the URL for a collection served by your own route, not a Nimbus route helper; for one that is, the route sets the URL and `prefix` is deprecated. |
| `{ label, items }` | Build a recursive manual group. Groups support `collapsed`, `badge`, and `icon`. |
| `{ segment, landing }` | Give a manual group ownership of a URL segment while linking its label and breadcrumbs to a real landing page. |

Array position controls manual item order. Nimbus does not re-sort a configured or transformed array.

## Nested collections

A collection served inside a docs folder's URL appears in that folder. With `src/content/docs/integrations/connectors/` and a `dbt` collection routed at `src/pages/integrations/connectors/dbt/[...slug].astro` (see [Collection URLs](/writing/pages-and-routing#collection-urls)), dbt is a group inside Connectors whose landing is `/integrations/connectors/dbt/`. Breadcrumbs and previous and next links follow, because they read the sidebar. A page the sidebar leaves out takes the breadcrumbs of the deepest group above its URL, then a crumb for each page between there and itself, titled like the page.

This works wherever the folder is generated: with no `sidebar.items`, inside `{ autogenerate: { collection: "docs" } }`, or inside `{ autogenerate: { directory } }`, including one inside a hand-made `{ label, items }` group. It's never placed directly among a hand-made group's own items. If folders between are missing, the collection goes in the deepest one that exists, and a folder whose only page is its `index` becomes a group to hold it, as it would with a second page. That group keeps the label the page had as a link, and drops its `Draft` badge, as any folder's group does.

The collection's own `index` page controls the group, as a folder's does. Set its label and position:

```yaml title="src/content/dbt/index.mdx"
---
title: dbt
sidebar:
  order: 2              # its position among the folder's pages; pages with an order come first,
                        # and a group without one takes its lowest child's
  group:
    label: dbt Core     # the group label; the title otherwise
---
```

With no `index` page, the group is a heading named after the URL's last segment (`Dbt`). Show only its landing link with `sidebar.hideChildren: true`, or leave the whole collection out of the sidebar, along with any collection served inside it, with `sidebar.hidden: true`.

To place it yourself, name it in `sidebar.items` with `{ autogenerate: { collection: "dbt" } }`, link to its URL with `{ label: "dbt", link: "/integrations/connectors/dbt/" }`, or make it a hand-made group's `landing`; it then appears only there. A link or a `landing` shows only the collection's landing page, and leaves out the collections served inside it; to show its pages and theirs, use `{ autogenerate: { collection } }`, with a `label` to make it a group with its landing. Without a `label`, its pages go straight into the surrounding group, so its landing page isn't linked and its `hideChildren` has no effect.

Not placed:

- a collection one segment deep (`/blog`), whose parent is the site root;
- an API collection, which has its own navigation;
- anything on another docs version's pages;
- a collection's alias routes (only the URL it's served at counts).

In `astro dev`, edits to a placed collection's pages under `src/content` show on reload. A collection loaded from elsewhere, or from a content source, shows changes to its navigation after a restart.

## Scope large sidebars

Large sites can progressively narrow the rail:

```ts title="astro.config.ts"
sidebar: {
  scope: "section",
  isolate: { boundaries: ["learning-paths/*", "reference/*"] },
  defaultCollapsed: true,
}
```

- `scope: "full"` is the default and renders the complete tree on every page.
- `scope: "section"` renders only the active top-level group. Pair it with section tabs or another cross-section navigation surface.
- `isolate.boundaries` descends again when a route matches a segment glob. `*` matches one path segment; non-matching routes are unchanged.
- `defaultCollapsed` closes groups by default. The active group still opens, and a group's explicit `collapsed` value wins.

Build section tabs from the same structural tree:

```astro
---
import { getSidebarSections } from "@cloudflare/nimbus-docs";

const sections = await getSidebarSections(currentSlug, {
  collection: entry.collection,
});
---
```

## Control group landing pages

A directory `index.mdx` is its group's landing page. Configure how those landings appear across the site in `astro.config.ts`:

```ts title="astro.config.ts"
sidebar: {
  indexDisplay: "overview-leaf",
  overviewLabel: "Overview",
}
```

| Option | Behavior |
|---|---|
| `indexDisplay: "header-link"` | Default. The group heading links to its landing page. |
| `indexDisplay: "overview-leaf"` | The group heading becomes a disclosure and the landing becomes its first child. |
| `overviewLabel: true` | Labels landing links `Overview`. A string supplies a custom label. |
| `sidebar.group.hideIndex: true` | Keeps the page built but makes its group heading non-interactive. |
| `sidebar.hideChildren: true` | Collapses the whole directory to one link to its landing page. |

## Transform the final tree

Configuration defines the structural tree. `getSidebar()` also accepts a synchronous or asynchronous `transform` for computed navigation. It runs after scope and isolation, but before `indexDisplay` reshapes landing pages.

```astro title="src/pages/[...slug].astro"
---
import { getPrevNext, getSidebar } from "@cloudflare/nimbus-docs";

const sidebar = await getSidebar(currentSlug, {
  collection: entry.collection,
  transform: ({ tree, sectionSlug }) => {
    if (sectionSlug !== "api") return tree;

    return tree.map((item) =>
      item.type === "group" && item.label === "Reference"
        ? {
            ...item,
            collapsed: false,
            badge: "API",
            children: [
              ...item.children,
              {
                type: "external",
                label: "API status",
                href: "https://status.example.com",
                order: Number.MAX_SAFE_INTEGER,
              },
            ],
          }
        : item,
    );
  },
});

const prevNext = await getPrevNext(currentSlug, {
  sidebarTree: sidebar,
});
---
```

The callback receives:

| Value | Meaning |
|---|---|
| `tree` | The cloned, active-state-aware `SidebarItem[]` for this page. Nodes are `link`, `external`, or recursive `group` items. |
| `currentSlug` | The complete current URL path. |
| `sectionSlug` | The first path segment. |
| `module` | The second path segment, when present. |
| `indexEntryId` | The active section group's landing entry ID, when it has one. |

A transform can fetch data, insert or remove nodes, rewrite nested groups, attach badges, or reorder the rail. Return rendered `SidebarItem` nodes, not config-only shapes such as `autogenerate`. Preserve existing properties when decorating nodes, and pass the result to `getPrevNext()` when pagination should follow the transformed order.

Transforms only affect the page rail. Breadcrumbs and `getSidebarSections()` continue to use the structural tree.

## Per-page controls

Use frontmatter for local changes:

| Field | Behavior |
|---|---|
| `sidebar: false` | Removes the sidebar column from this page. |
| `sidebar.order` | Orders an entry inside an autogenerated group. |
| `sidebar.label` | Overrides the page title in the rail. |
| `sidebar.badge` | Adds a string or styled badge. |
| `sidebar.hidden` | Builds the page but removes it from the rail. |
| `sidebar.group.label` | Overrides the directory group's label from its `index.mdx`. |
| `sidebar.group.badge` | Adds a badge to the directory group. |
| `sidebar.group.icon` | Adds an `astro-icon` icon to the directory group. |
| `sidebar.group.hideIndex` | Prevents the directory group heading from linking to its index. |
| `sidebar.hideChildren` or `hideChildren` | Collapses the directory to its landing link. |
| `external_link` | Rewrites the sidebar destination to another internal path or an external URL. |

Set `features.sidebar: false` in `astro.config.ts` to disable the rail site-wide. See [Frontmatter](/writing/frontmatter) for complete field shapes and badge variants.

## Markup and styling hooks

Sidebar groups are native `<details>`/`<summary>` elements: opening and closing needs no JavaScript, links in closed groups stay in the HTML for find-in-page and crawlers, and closed lists carry `display: none` so large trees stay fast. A group with a landing page lists it as the group's first child, labelled "Overview" — the summary row is label-only.

Rows carry no class or data attribute, so a sidebar of thousands of pages stays light. The "Sidebar rows" section of `src/styles/globals.css` styles them by position inside the sidebar (`[data-nb-sidebar]`, and `[data-nb-api-nav]` for the API reference). Edit those rules to restyle every row. They sit in Tailwind's `components` layer, so a Tailwind utility on a row still overrides them:

| Selector | Element |
|---|---|
| `[data-nb-sidebar] li > a` | A leaf row: `<a href>Label</a>`. The current page carries `aria-current="page"`. |
| `[data-nb-sidebar] details > summary` | A group's row. The caret is its `::after` mask, rotated by `details[open]`; the active trail carries `data-nb-active`. |
| `[data-nb-sidebar] details > ul` | A group's child list. |
| `i[data-m]` | An API operation's method chip; `data-m` is the lowercase method. |

The `.nb-sidebar-link`, `.nb-sidebar-row` and `.nb-sidebar-list` classes still style an element that carries them, for a row placed elsewhere. Sites that styled rows by those classes or by the old `data-nb-sidebar-*` attributes switch to the selectors above; the `lighter-sidebar-rows` upgrade entry lists the steps.

Each page renders one sidebar tree: the mobile drawer borrows the rail's tree while it is open and returns it on close, so open groups, the filter, and scroll position stay with you across the breakpoint.

Upgrading from the scripted-collapsible markup: run `nimbus-docs outdated` to see which files changed, and `nimbus-docs diff <file> --apply` to update them. Update these together, since a partial update breaks the sidebar's styling or its saved open groups:

- `src/components/ui/sidebar/*`
- `src/layouts/DocsLayout.astro`
- `src/styles/globals.css` (if you edited it, copy in the "Sidebar rows" section by hand)
- With an API reference, last: the `api-sidebar` and `api-layout` registry components. These come from the registry, not the starter, so reinstall them with `nimbus-docs add api-sidebar --overwrite` and `nimbus-docs add api-layout --overwrite`. Commit first: reinstalling also replaces the components they depend on, including `src/components/ui/sidebar/*`, so review the change with `git diff` and reapply your own edits.

If you edited these files, you can keep your copies: the framework's state scripts drive both the old and the new markup. Port your edits when convenient. Groups with a landing page now show it as an "Overview" child row instead of a split label/caret header.
